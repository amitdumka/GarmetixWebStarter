# Learnings / Codebase Notes

Non-obvious facts discovered while exploring, kept here so future sessions don't have to re-derive them.

- **Two "legacy" folders exist and mean different things.** `frontend/legacy/garmetix-web` is the actual live legacy Nuxt app. Root-level `legacy/` is a different thing: deployment notes, release notes (`RELEASE-v4.12.*.txt`), device-bridge companion apps (`Garmetix.AttendanceKiosk`, `Garmetix.FingerprintBridge`, `Garmetix.MantraMockService`), and Docker/Cloudflare/Ubuntu ops scripts. Don't confuse the two when a task says "legacy."
- **The project has been through a full legacy-baseline replacement (Version6).** Per `docs/VERSION6_LEGACY_BASELINE_MIGRATION_ROADMAP.md` (2026-07-03), legacy was rebased onto an incoming v4.12.69 package (Stage 11D), and modular work was paused/resumed around that. If something in modular looks like it's missing a legacy feature, check whether it predates that baseline swap.
- **`backend/Garmetix.Domain/Generated/` is scaffolded/generated code** (references to a "Bharat" toolkit in comments - `BharatEnums.cs`, calculator TODOs). Treat as generated: prefer patching in `Garmetix.Api`/`Garmetix.Infrastructure` over hand-editing generated models unless the task is specifically about the generator output.
- **Admin factory reset is Admin-policy-gated, not SuperAdmin-only**, despite the intent recorded in Stage 13F closure notes. Confirmed 2026-07-07 in `backend/Garmetix.Api/Backup/FactoryResetEndpoints.cs:17` - `RequireAuthorization(GarmetixPolicies.Admin)`. This is a known, previously-flagged gap (see `roadmap.md`/bug list), not a new find, but still open.
- **CRLF vs LF noise**: see `environment.md`. Don't report "1,689 uncommitted files" as a real problem - it's a line-ending diff artifact of viewing a Windows checkout from the Linux sandbox.
- **The modular scripts folder (`frontend/modular/scripts/`) is huge (~80 files) and follows a strict per-module pattern**: `*-parity-baseline`, `*-contract-check` / `*-contract`, `*-browser-acceptance`, `*-readiness`, `*-final-closure` / `*-stageXX-closure`. When adding a new module or stage, follow this naming/lifecycle convention rather than inventing a new one.
- **Assistant/AI feature is live-flagged off by default** (`Assistant__Enabled`), and the modular launcher only shows when both a token exists and `NUXT_PUBLIC_GARMETIX_ASSISTANT_ENABLED=true`. An Anthropic API key was pasted into chat during intake (per `.codex/Assistant_MCP_AI_Sense_TODO.md`) and flagged for rotation - confirm with Amit it was actually rotated before ever enabling this live.
- **Route ownership is centralized** in `frontend/modular/config/routes.ts` - always check/update this when adding or moving a page between modular apps, rather than only editing the app's own `pages/`.
- Full stage history (12A through 14F.6C) is narrated in `frontend/modular/docs/MODULAR_TODO.md` - read that before assuming a feature doesn't exist; it's very likely already built and just needs live-evidence validation, not re-implementation.
- **A normal EF Core migration file is NOT enough to change the live SRP database schema - confirmed 2026-07-10.** The SRP host runs with `Database:SchemaBootstrapMode=FreshBaseline` (or similar EnsureCreated variant), which makes `ApplyDatabaseStartupMigrationsAsync` in `backend/Garmetix.Api/Program.cs` call `EnsureCreatedAsync()` + mark a baseline migration row and **return early** - it never reaches `db.Database.MigrateAsync()`, so individual dated migration files under `backend/Garmetix.Infrastructure/Data/Migrations/` are never actually applied on that box. The mechanism that *actually* keeps the live schema in sync is a separate, hand-maintained idempotent service: `backend/Garmetix.Api/Database/DatabaseSchemaRepairService.cs`, specifically `RepairKnownSchemaDriftAsync` (called unconditionally on every API startup from `Program.cs`), which contains explicit `ALTER TABLE "X" ADD COLUMN IF NOT EXISTS "Y" type NULL;` statements per column. **Any future column/table addition needs a matching entry added to this file, not just a migration class** - the migration file is still worth adding for local/dev environments and as documentation of intent, but treat `DatabaseSchemaRepairService.cs` as the actually load-bearing artifact for this production host. Discovered by reading the real post-restart `journalctl` output line-by-line after a migration silently didn't apply - don't trust "the migration file compiles and the app starts cleanly" as proof a schema change reached production; verify via the live log (search for the exact column name in `journalctl -u garmetix-srp-api.service` right after a restart) or a direct schema query.
