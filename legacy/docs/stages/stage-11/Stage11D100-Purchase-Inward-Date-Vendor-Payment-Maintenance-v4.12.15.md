# Stage 11D-100 — Purchase Inward Date + Vendor Payment Maintenance

Version: `4.12.15`
Build code: `GARMETIX-11D100-20260629-4214`
Base: `v4.12.14 Stage 11D-99 Vyapar Historical Stock Bridge Fix`

## Purpose

This stage removes two operational restrictions that can create wrong data:

1. Purchase inward date can now be selected on new/edit purchase inward instead of always using the server date.
2. Vendor payment entries can now be viewed, edited and deleted from the Purchase page so wrong payment entries can be corrected safely.

## Purchase inward date changes

### Frontend

Updated pages:

- `frontend/garmetix-web/pages/purchase/new.vue`
- `frontend/garmetix-web/pages/purchase/index.vue`

Added/confirmed fields:

- New Purchase Inward page includes `Inward date`.
- Inline New Purchase Inward modal includes `Inward date`.
- Edit Purchase Inward modal keeps `Inward date`.

### Backend

Updated files:

- `backend/Garmetix.Api/Purchase/PurchaseDtos.cs`
- `backend/Garmetix.Api/Purchase/PurchaseEndpoints.cs`
- `backend/Garmetix.Api/PurchaseImport/PurchaseInvoiceImportService.cs`
- `backend/Garmetix.Api/Numbering/DocumentNumberService.cs`

New purchase inward request field:

```csharp
DateTime? InwardDate
```

The selected inward date now controls:

- `PurchaseInvoice.InwardDate`
- purchase stock movement `OnDate`
- first inward payment row `OnDate`
- purchase inward number month/sequence when generated by server

Supplier invoice date still controls `PurchaseInvoice.OnDate` when supplied; otherwise it falls back to inward date.

When editing an existing purchase inward and changing `InwardDate`, linked active purchase stock movements are moved to the same date so ledger history follows the corrected inward date.

## Vendor payment maintenance

### Backend APIs

Added/expanded APIs:

```http
GET    /api/purchase/payments/recent
GET    /api/purchase/payments/{id}
PUT    /api/purchase/payments/{id}
DELETE /api/purchase/payments/{id}
```

`GET /payments/recent` now returns more fields for maintenance:

- payment mode value and label
- bank account id
- reference number
- payment details
- remarks
- voucher id and voucher number

### Frontend

The Purchase page now includes a `Vendor Payments` register with:

- View
- Edit
- Delete

Edit supports:

- payment date
- amount
- payment mode
- bank account for non-cash payments
- reference / UTR / cheque number
- payment details
- remarks

Delete soft-removes the vendor payment and linked active voucher/bank/accounting rows where available, then recalculates vendor/invoice status.

## Safety notes

- This stage does not add a database migration.
- Existing purchase inward records are not automatically rewritten.
- Existing vendor payment entries stay intact until edited/deleted by an authorized user.
- Vendor payment delete is soft-delete style for operational safety, not physical hard delete.
