## 2026-07-07 - Fixed a broken SRP deploy: Nitro flaky-build bug + npm workspace pin bug

Amit reported that opening the just-deployed GST pages showed "redirecting" or downloaded a text file instead of rendering - traced this to every page of every app (not just GST, not just Books) being reduced to a 16-byte `"Redirecting..."` stub with `Content-Type: application/octet-stream` on the live SRP site. Root-caused precisely, in order of discovery:

1. **Immediate action**: rolled back `/opt/garmetix-srp/current` on the server to the last known-good release (asked Amit first, since it's a manual write to a shared server outside the normal deploy process) to restore the site while investigating.
2. **Root cause of the broken content**: Nitro's static-generation crawler was 404ing on every route during a *cold* build, and Nitro's own internal error handler (`nitropack/dist/core/index.mjs`, the `defaultHandler` 404-with-baseURL-mismatch branch) converts that into a redirect response with body `"Redirecting..."`, which the static generator then writes to disk as the page's entire content. Confirmed this is **flaky/non-deterministic**: a fully clean build (no `.nuxt`, no cache) either crashes outright (`createRequire` given a malformed `file:///_entry.js` URL) or silently produces this degenerate output; an immediate retry using leftover state from the failed/degenerate attempt reliably produces correct output. Not caused by anything in this session's source changes - reproduced identically on apps never touched (pos, hr, ai-sense, main).
3. **Fix**: added a build-retry-with-content-verification safety net directly to `frontend/modular/deploy/srp-whole-site-deploy.sh`'s `build_app()` - it now checks `index.html` size after each build attempt (>200 bytes) and retries up to 3 times without re-clearing the Nuxt cache (clearing the cache before every retry would just reproduce the cold-start crash), refusing to stage a broken release if all attempts fail.
4. **Separate bug found while restoring `node_modules`** (a routine `npm ci`/`npm install` deleted it and then failed to reinstall): every app's `package.json` pins internal `@garmetix/shared-*` workspace dependencies at an exact stale version string (`"6.0.0"`) that doesn't match the actual current package versions (e.g. `shared-api` is at `6.0.51`). This mismatch makes npm 11.13 attempt a registry manifest fetch for these private/unpublished package names, which 404s and fails the entire install. Fixed by relaxing all these pins to `"*"` across 7 apps + 3 shared packages (`git diff` confirms this was a pin-only change, all still resolve to the local workspace links).
5. **Separate, orthogonal bug hit mid-fix**: the SRP deploy script's `dotnet publish` step fails specifically when run through Git Bash (not WSL) with a doubled drive-letter path (`C:\c\AIArea\...`). Worked around for this deploy via `--skip-api` (no backend changes existed anyway); root cause not fixed - flagged as a follow-up (see `.claude/todo.md`).
6. Redeployed with the retry-safe script; verified via direct SSH file-content checks and `srp-public-acceptance.mjs --live --strict` - now genuinely all-green, including the asset-reference checks that were silently "missing-assets" warnings in the first (broken) deploy's acceptance run. **Lesson for future deploys**: HTTP-status-only acceptance checks are not sufficient - verify actual served content, not just response codes.
