# Stage 14I: HR Module UX Overhaul + Deploy Tooling

## Context

Amit requested a large, itemized overhaul of the modular HR app (`frontend/modular/apps/hr`), moving it up to the same UX standard established in Stage 14H for Books/POS: modal/slideover forms instead of always-visible inline forms, edit/delete everywhere the backend supports it, pagination/filtering on any list that can grow large, user-readable error/data display instead of raw JSON, and a faithful port of legacy features that are missing in modular (ID card, Employee list shape, Monthly Attendance generation semantics).

A full research pass (Explore agent) mapped every HR page in modular and legacy plus every relevant backend endpoint before any code was touched. Findings are summarized inline per item below; the full report is preserved in session history.

## Global standard (applies to every item below)

- **Form size rule** (carried over from the Books stage): big field count → dedicated page or `USlideover`; medium field count → `UModal`; small field count → `UModal` or inline mini-form. Default to `UModal` unless a page already has a good reason for `USlideover` (matches existing CRM/HR precedent).
- **Row actions**: every list/table gets Edit + Delete buttons wherever the backend has a corresponding write/delete endpoint. Where the backend only has "revoke" (Devices, Biometric Enrollments) or no delete at all (Attendance Policies today), either add the missing endpoint (small, low-risk, mirrors an existing sibling endpoint) or use the closest equivalent action and label it honestly.
- **Pagination/filter**: any table that can grow unbounded (Employees, Attendance, Monthly Attendance, Payroll lists, Regularization, Salary Draft/Payment) gets a status/date filter plus simple page/pageSize controls, matching the pattern already used in POS `history.vue`/`returns.vue`.
- **Readable errors/data**: replace raw `JSON.stringify(...)`/technical exception text shown directly in the UI with plain-language summaries; point users to the existing Message Logs page for full technical detail instead of dumping it inline.
- **No backend changes beyond small, low-risk, additive ones** that mirror an already-existing sibling pattern in the same file (e.g. adding `DELETE /api/attendance/policies/{id}` next to the existing Shifts/ShiftRules delete routes). Nothing structural, no new tables, no migrations.

## Item-by-item plan

1. **Employees route rename** (`/hr/hr` → `/hr/employees`): update `routes.ts`'s `hr` route id's path only; the page file (`pages/hr.vue`) does not need to move since Nuxt page-to-route mapping goes through the shell route registry, not file-based routing, for the `hr` app's root-level pages actually it's file-based — need to add `pages/employees.vue` (or rename `hr.vue`) so the URL segment changes. Confirm exact mechanism before editing.
2. **Employee / Attendance New-Edit as modal/slideover**: `pages/hr.vue`'s Employee tab and Attendance tab forms are both always-visible inline (610 lines total) — convert both to `UModal`/`USlideover` per the size rule (Employee form is bigger → slideover; Attendance form is smaller → modal), matching legacy's own choice (`UiFormSlideover` with `layout="modal"` for Employee, `layout="slideover"` for Attendance — modular will use `UModal`/`USlideover` directly, no new wrapper component, consistent with the "no FormSlideover port" decision from Stage 14H).
3. **Edit/Delete audit across all three `hr.vue` tabs**: Employee tab already has Edit+Delete. Attendance tab already has Edit+Delete. Monthly Generation tab is a trigger-only tab (no rows to edit) — no gap here, confirm and note as already-complete.
4. **Monthly Attendance generation**: confirmed same endpoint (`POST api/hr/monthly-attendance/generate`) already wired in modular `hr.vue`, matching legacy's `generateMonthlyAttendance()`. Legacy also auto-triggers on month rollover via a `localStorage` guard key — port that auto-trigger behavior into modular for parity. Confirm the endpoint already filters to active employees (per `MonthlyAttendanceService.GenerateAsync`) — if so, item is mostly about UX polish + auto-trigger, not new logic.
5. **Employee list column/action shape**: port legacy's exact row shape (Code, Employee, Mobile masked, Department, Designation, Salary, Joining, Status badge, Edit/ID Card/Delete actions) into modular's employee table, including `maskMobile()`.
6. **ID Card generation**: port legacy's `GET api/hr/employees/{id}/id-card` + `UModal` card view + `window.print()` client-side print into modular (no backend PDF endpoint exists or is needed — legacy doesn't have one either, it's browser print of the modal DOM).
7. **Pagination + filter on Employees/Attendance/Monthly tables**: Employees currently has only a text search (no paging) — add simple page/pageSize. Attendance tab in modular has no paging at all (legacy's does, via `GET api/hr/attendance?page&pageSize`) — wire that in. Monthly Attendance page (`attendance/monthly.vue`) currently renders the full list client-side with no paging — add client or server paging (backend list for monthly attendance is generic `/api/monthly-attendance`, no page/pageSize query support server-side, so this will be client-side pagination over the fetched list, consistent with what legacy itself does there).
8. **Payroll Summary redesign** (`attendance/payroll-summary.vue`, 106 lines): currently a thin read-only CSV-export view. Redesign around real KPI cards, a readable per-employee breakdown table, and clearer date/period controls — reference `MODULAR_TODO.md`/roadmap for any prior notes on this page's intended scope before rebuilding.
9. **Payroll forms as modal/slideover**: `pages/payroll.vue` (848 lines, 3 tabs: Payslips/Salary Structures/Salary Payments) — all inline today. Convert Salary Structure create/edit (small-medium fields) to `UModal`, Salary Payment create/edit (larger, has preview/PDF) to `USlideover`. Payslips tab is generate+list, not a create form — no modal needed there beyond an edit modal if editing a payslip row is wanted (reuse generic `/api/salary-pay-slips` PUT/DELETE, currently unused by the UI).
10. **Salary Payment sub-menu item industry-standard pass**: `attendance/salary-payment.vue` (333 lines) — add proper Create/Edit/Delete/View using `/api/salary-payments` full CRUD (already exists server-side, just needs a delete button + edit form + view detail wired into the UI, moved into modal/slideover instead of inline).
11. **Salary Draft standardization**: `attendance/salary-draft.vue` (289 lines) — clean up into an industry-standard list (readable status, clear actions), replace any raw technical error text with plain messages, point to Message Logs for detail.
12. **Regularization readable view**: `attendance/regularization.vue` (300 lines) — currently likely surfaces raw JSON/technical fields for request detail; give it a proper readable summary view (who/when/what/why, before-after) instead.
13. **Monthly (attendance/monthly.vue) same treatment**: apply the same global standard (modal/slideover for any inline form, pagination, readable errors) already covered by items 7/12's pattern.
14. **Attendance Shifts / Shift Rules / Attendance Policies global standard**: all three already have decent CRUD (Shifts/ShiftRules full CRUD; Policies missing DELETE — add it, mirroring the existing Shifts/ShiftRules delete route in `Attendance/AttendanceEndpoints.cs`). Convert their inline forms to modal/slideover, add filter/pagination since shift-rules especially can grow with employee count.
15. **HR Benefits CRUD completion**: `pages/hr-benefits.vue` (351 lines) already has full CRUD against `/api/hr-payroll/adjustments` — audit against the "Benefit" domain concept (advance/recovery/leave/bonus/encashment/PF/gratuity) for any missing field/action, convert the inline form to modal per the global standard.
16. **Deploy only changed modules**: the deploy script (`srp-whole-site-deploy.sh`) currently has no per-app selection flag, only `--skip-api`/`--skip-build`. Add a lightweight `--apps=hr,books,...` filter so only touched Nuxt apps rebuild+redeploy, making iterative deploys fast. Also carries forward the known Git-Bash-vs-WSL split: WSL builds the API correctly but can't find the trusted SSH key (lives in Git Bash's home dir); Git Bash has the SSH key but hits a doubled-drive-letter `dotnet publish` bug. Until that's root-caused, API-touching deploys should run via WSL specifically for the API step (or accept `--skip-api` and deploy the API separately when it actually changes).
17. (Guidance, not a deliverable: use judgment throughout, matching established Books-stage conventions.)
18. **Commit + version bump**: small commits per completed item (per the standing rule), single version bump at the end of the stage.
19. **Final pending-items report**: delivered as a plain status summary once this stage's work stops, listing anything not completed and why.

## Sequencing

Work roughly in the order listed above since later items depend on the global-standard pattern established by the earlier ones (route rename and Employee/Attendance modal conversion first, then the rest of Attendance sub-pages, then Payroll, then Benefits, then deploy tooling last).
